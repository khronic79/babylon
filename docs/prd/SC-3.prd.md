# SC-3: Атомарная инициализация прокси (H-02)

Status: PRD_READY
stage: IMPLEMENT

## Контекст / идея

Согласно аудиту `docs/audit-reports/2026-08-20.md`, находка **H-02 (High)**: функция
`initialize` контракта `SettelmentsControl` защищена только OZ-модификатором
`initializer` (однократный вызов), но **без** ограничения по `msg.sender`. Текущий
конструктор прокси деплоит его с пустыми данными
(`constructor(address implementation) ERC1967Proxy(implementation, "")`), а
`initialize` вызывается отдельной транзакцией. Поэтому любой наблюдатель может
фронт-ранить эту транзакцию, первым вызвать `initialize` и стать админом/владельцем
контракта (захват средств и управляющих функций).

**Выбранное решение (обсуждено с пользователем):** атомарная инициализация через
конструктор прокси — вариант 2 (канонический паттерн OpenZeppelin). Конструктор
прокси принимает `bytes memory data` и пробрасывает их в базовый `ERC1967Proxy`,
который выполняет `initialize` атомарно в рамках транзакции деплоя прокси.

**Скоуп SC-3** — единственный изменяемый файл `contracts/SettelmentsControlProxy.sol`.
`SettelmentsControl.sol` **не меняется**: модификатор `initializer` уже корректен —
при `delegatecall` из конструктора прокси хранилище прокси пустое, поэтому
`initializer` проходит; прямая инициализация имплементации блокируется
`_disableInitializers()` в её конструкторе.

Deploy-скрипт (`scripts/deploy.ts`) **не меняется и не пишется** в рамках этой задачи
(деплой вынесен отдельно и далеко впереди).

## Цели

- Изменить конструктор `SettelmentsControlProxy`, чтобы он принимал
  `(address implementation, bytes memory data)` и пробрасывал `data` в базовый
  `ERC1967Proxy`, обеспечивая атомарное выполнение `initialize` в транзакции
  деплоя прокси:
  ```solidity
  constructor(address implementation, bytes memory data)
      ERC1967Proxy(implementation, data) {
      ERC1967Utils.changeAdmin(msg.sender);
  }
  ```
- Сохранить `ERC1967Utils.changeAdmin(msg.sender)` в конструкторе — деплойер
  прокси автоматически становится админом прокси.
- Не менять остальные части прокси: `receive` с `NotAcceptEtherDirectly`,
  `changeProxyAdmin`, `getProxyAdmin`, `getImpl`, `setImpl`.
- Не менять `SettelmentsControl.sol` (модификатор `initializer` и
  `_disableInitializers()` уже корректны).
- Закрыть находку H-02 в части «фронт-раннинг инициализации». Часть «deploy-скрипт
  передаёт неверное число аргументов» остаётся отдельной задачей (вне замечаний
  аудита, вне скоупа SC-3).

## User stories

- Как деплойер, я хочу развернуть прокси и инициализировать его в **одной**
  транзакции (передавая `data = abi.encodeCall(initialize, (...))` в конструктор),
  чтобы никто не мог фронт-ранить инициализацию и захватить админа/владельца.
- Как разработчик, я хочу, чтобы прокси-контракт использовал канонический
  конструктор OpenZeppelin `(implementation, data)`, чтобы применять стандартный,
  проверенный паттерн вместо кастомных защит инициализатора.
- Как оператор, я хочу, чтобы деплойер прокси автоматически становился админом
  прокси (`changeAdmin(msg.sender)`), сохраняя существующую модель управления
  прокси.

## Основные сценарии

1. **Атомарный деплой:** конструктор вызывается с
   `(implementation, data)`, где `data = abi.encodeCall(initialize, (...))`.
   `ERC1967Proxy` выполняет `delegatecall` на `initialize`; хранилище прокси пустое,
   поэтому модификатор `initializer` проходит; инициализация и назначение админа
   прокси (`changeAdmin(msg.sender)`) происходят в одной транзакции.
2. **Прямая инициализация имплементации:** вызов `initialize` напрямую на
   имплементации ревертится, т.к. `_disableInitializers()` в её конструкторе уже
   заблокировал инициализаторы (существующее поведение, не меняется).
3. **Пустые `data`:** если развернуть прокси с `data = ""`, прокси останется
   неинициализированным (контракт сам это не принуждает) — это осознанный trade-off
   канонического паттерна; ответственность за непустые `data` лежит на будущем
   deploy-скрипте (вне скоупа SC-3).
4. **Повторная инициализация через прокси:** после атомарного деплоя повторный вызов
   `initialize` ревертится модификатором `initializer` (существующее поведение).
5. **Прочие функции прокси:** `changeProxyAdmin`, `getProxyAdmin`, `getImpl`,
   `setImpl`, блокировка приёма ETH (`NotAcceptEtherDirectly`) — без изменений.

## Успех / метрики

- **Критерий успеха — успешная чистая компиляция:**
  `rm -rf artifacts cache && npx hardhat compile` возвращает код 0.
- Конструктор прокси имеет сигнатуру `(address implementation, bytes memory data)`
  и пробрасывает `data` в `ERC1967Proxy(implementation, data)`.
- `changeAdmin(msg.sender)` в конструкторе сохранён.
- Функции `receive`, `changeProxyAdmin`, `getProxyAdmin`, `getImpl`, `setImpl`
  не изменены.
- `SettelmentsControl.sol` не изменён.
- Тесты, deploy-скрипт, сабграф — вне скоупа и не являются критерием приёмки.

## Ограничения и допущения

- Область задачи — только `contracts/SettelmentsControlProxy.sol` (конструктор).
- Deploy-скрипт `scripts/deploy.ts` **не меняется и не пишется** (деплой вынесен
  отдельно).
- Защита от фронт-раннинга в варианте 2 обеспечивается процессом деплоя, а не
  самим контрактом: deploy-скрипт обязан всегда передавать непустые `data` в
  конструктор прокси. Контракт не принуждает передавать `data` — это осознанный
  trade-off канонического паттерна.
- Изменение сигнатуры конструктора меняет ABI прокси: в том числе для верификации
  на etherscan потребуется передавать аргументы `(implementation, data)`.
- Модификатор `initializer` в `SettelmentsControl.sol` остаётся без изменений и уже
  корректен для атомарной инициализации через конструктор прокси.

## Риски

- Если будущий deploy-скрипт передаст пустые `data`, прокси останется
  неинициализированным и снова уязвимым к фронт-раннингу — контракт это не
  предотвращает; защита целиком зависит от корректности deploy-процесса.
- Изменение сигнатуры конструктора прокси ломает текущий `scripts/deploy.ts`
  (передаёт только `implAddress`) и процесс верификации — это осознанно и вынесено
  в отдельную задачу (вне скоупа SC-3).
- Атомарность: `changeAdmin(msg.sender)` выполняется после `delegatecall` на
  `initialize`; если `initialize` ревертится, вся транзакция деплоя ревертится —
  частично инициализированного состояния не возникает (желаемое поведение).
- Смена ABI прокси затрагивает off-chain потребителей ABI прокси (не
  `SettelmentsControl`) — вне скоупа.

## Открытые вопросы

- (неблокирующее) Формирование `data` (`abi.encodeCall(initialize, ...)`) с пятью
  аргументами `initialize` и исправление «неверного числа аргументов» в
  `scripts/deploy.ts` — относится к будущей задаче деплоя, вне скоупа SC-3.
- (неблокирующее) Соотношение ролей: админ прокси (`changeAdmin(msg.sender)`) и
  админ/владелец контракта (`_admin`/`_owner` из `initialize`) — уточняется на
  этапе планирования деплоя, вне скоупа SC-3.
